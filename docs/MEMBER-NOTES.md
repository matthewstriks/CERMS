# Member notes and admission reasons

Member View now includes a staff note log. Any signed-in staff member in the member's saved business may add a note. Each new entry records the authenticated UID, the name read from that staff member's existing profile, and a server timestamp. Names and timestamps cannot be supplied by the desktop. Existing embedded notes remain visible with their original text and attribution; no backfill or attribution is invented. New-membership checkout notes also use this structured log and the verified creator name.

The owner retains full access. The independent optional **Remove member notes** permission can be assigned through Users & permissions and defaults off for other existing staff. Removal requires confirmation. Removing a structured note clears its text, preserves a deletion marker and verified remover/time, and removes it from the displayed log. Legacy embedded-note removal affects only the selected original entry and records an idempotency marker; duplicate text cannot cause a retry to remove another note. Removing a DNA reason does not clear the member's DNA status. Existing member deletion does not cascade into these business note records.

DNA changes are managed in the member notes section by staff with `editMembers`. Checking **Do not admit (DNA)** reveals a required reason. The server atomically changes the member's DNA flag and creates a highlighted **DNA · Do not admit** note. Clearing DNA creates a separate attributed clearance note and retains earlier reasons. Revision/status checks reject stale changes. The generic member editor retains **Read notes / tagged**; it cannot change DNA directly. Rules enforce this restriction even for older desktop clients. Existing DNA members are not backfilled or automatically changed.

The member's existing `tag` flag controls mandatory order review. Starting/linking an existing member or assigning an existing rental/membership recipient loads current notes; tagged participants show **Read member notes** with their notes and a **Confirm read** button. Cancellation grants no acknowledgement. Each involved member must be acknowledged independently. Payment rechecks notes, and atomic `completeSale` rejects missing or outdated revision acknowledgements. New notes, DNA changes and removals advance `notesRevision`, so notes changed after acknowledgement must be reviewed again. Failed loading blocks payment. Successful-sale retries retain their original request and retrieve the saved receipt even if notes later change. Acknowledgements are reset for a new order; note text is never put into POS local storage or customer receipts. Reading a DNA note does not grant permission to admit or renew that member.

`memberNotes` is an authenticated callable restricted to named `cerms`, with `list`, `add`, `remove` and `dna` actions. Structured entries live at `system/{business}/memberNotes/{memberId}/entries/{noteId}`; legacy removal markers use the sibling `removedLegacy` collection. Only the callable writes these paths or the member's notes revision. List reads are paginated in batches of 50 and the client loads every page, rejecting a changed revision during pagination. Original member fields, identity reservations, sales, registers, Auth and Storage remain outside note mutations. Direct note Firestore access remains denied.
