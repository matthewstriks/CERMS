# Active rental management

Overview and Admissions & rentals share the View dialog. The fixed owner and staff with saved-business `processSales` permission can edit Assigned Room/Number and visit notes, toggle Inside/Outside and waitlist, and start rental renewal. Other staff retain read-only details. In/out changes location status only; it does not end a visit, release an admission claim, or check out a member.

`updateRental` runs only against named `cerms`, verifies saved business and current sales permission inside a transaction, and requires an active rental that is not going inactive. It accepts only room, notes, in/out and waitlist plus a revision check. Conflicting edits fail for review; expiry, member, product, visit ownership and payment fields cannot be edited. Existing records begin at revision zero without backfill. Renewal and edits preserve one another through transactional reads.

Renew in order opens normal POS with an existing-member link and a selected active, permitted rental product. The rental assignment carries `renewalVisitId`; its recipient and room are fixed in POS. Other order items remain available. A room or note edit must be saved before renewal. The operator may choose the rental duration/product for purchase without changing the original rental type or assignment.

`completeSale` validates the paid rental unit and target visit, business and recipient. It updates expiry atomically with the receipt, inventory and register totals, using `max(current expiry, server checkout time) + configured product duration`. No time is added while selecting a product, canceling payment, or after failed checkout. Identical-request retries return the saved receipt without repeating fulfillment. A visit may be renewed once per order and any number of times in separate paid orders. Renewals do not create visits/claims or mutate existing member profiles. Receipt assignments identify renewals and use the server's current room, never a stale client room.

No direct desktop activity writes, unrestricted time edits, visit check-out, rental deletion, refunds, legacy migrations or Auth/Storage changes are included. Current rules remain `firebase/releases/checkout-2026-10-11.rules`; direct activity writes stay denied. Deployment targets only `functions:cerms-staff:completeSale,functions:cerms-staff:updateRental` via `firebase.checkout.json`. Read-only `scripts/rental-deployment.mjs before|after` compares both databases' settings/indexes, all rules releases, both buckets and every other function. Evidence is saved in `docs/RENTAL-MANAGEMENT-DEPLOYMENT.json` after deployment.

Validation: `npm run check`, `npm run test:rules`, `node --test functions/pos.test.mjs`, and intercepted `node scripts/pos-smoke.mjs --members` / `--group`. Rebuild shared member encoding with `npm run build:checkout-domain` before deployment. All test records, edits, payments and print jobs are synthetic; no production test writes.
