# POS images, categories and favorites

Upload images in **Products → Create/Edit product → Product image**, then Save. JPEG, PNG and WebP originals have no application file-size or dimension cutoff. A square image around 512 × 512 is recommended, never required. Larger originals are optimized automatically into a display copy before upload. Mark **Favorite** in the product configuration to show it in the pinned top Favorites section. No additional upload or catalog-management permission is granted by this POS update.

POS product tiles use a saved image in place of the visible name/details when it can be loaded. Prices stay visible; the button retains the product name as its accessible label and hover title. Without an image, while loading, or on an image failure, the tile displays usable product text. Image loading is deferred until tiles approach the viewport. A bounded cache scoped to the signed-in business/client shares reads between Favorites and category tiles and is discarded when the client/session changes. Images use authenticated callable reads and data URLs, with no public Storage links.

Categories appear as native collapsible sections showing the configured name/color and matching product count. They start collapsed when POS first opens and can be toggled by mouse or keyboard. Searching or selecting a category opens relevant sections; clearing both returns sections to collapsed. Products whose category is unavailable appear under Uncategorized. Favorites stay above the category list, retain their own scroll area, and remain visible when categories are collapsed or search/category filters change. A favorite is also available inside its category. Active-product, staff restriction, stock and rental-selection eligibility checks still apply to all tiles.

`getProductImage` now admits staff with `processSales` for read-only POS access, as well as the original owner/catalog-manager readers. POS-only staff can read only attached images for active products permitted to their UID in their saved business. Inactive/restricted/unattached/foreign-business image requests are denied. Catalog managers keep editor previews for inactive products. `uploadProductImage` still requires catalog management and immutable private-bucket writes; upload authorization, server transport/processing bounds and object preservation are unchanged; source files are optimized locally to fit that transport rather than rejected. The desktop mirrors the read/write permission separation.

Verification includes three synthetic image-service tests (normalization/idempotency plus separate cashier read authorization and upload denial), the intercepted existing image-upload/editor flow, and `node scripts/pos-smoke.mjs --catalog` for image tiles, accessible names, text/error fallback, collapse/expand, keyboard operation, persistent favorites through search/category filters, deduplicated reads and cart additions. The group checkout regression remains intercepted. `npm run test:pos-catalog` runs the image/catalog checks sequentially. No live image uploads, product changes, sales, staff-account changes or print jobs are used for testing.

Deployment is limited to `functions:cerms-staff:getProductImage` using `firebase.product-images.json` under standing compatibility authorization. Named-cerms rules stay at `firebase/releases/checkout-2026-10-11.rules`. Read-only `scripts/checkout-deployment.mjs before|after --images` checks both databases/configurations/indexes, all rules releases, every other function, the legacy bucket and the isolated private image bucket. No Storage rules/bucket configuration, indexes, Auth or other backend services are changed. Evidence: `docs/POS-CATALOG-DEPLOYMENT.json` after deployment verification.
