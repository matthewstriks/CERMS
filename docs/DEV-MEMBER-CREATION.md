## Storage and query design

- `members/{requestUuid}` uses a stable random document ID for relationships and idempotent retries. A nine-digit numeric `id_number` is the human-facing number; it is not the document ID.
- Existing display fields and types remain readable by the current member adapter. New records add `schemaVersion: 2`, `createdBy`, `productId`, `fingerprint`, `identityKey`, and normalized `searchFirst`, `searchLast`, `searchName`, `searchId`, and `searchEmail` strings.
- Names retain their spelling. Search keys fold case/diacritics and collapse whitespace. ID search preserves leading zeros and punctuation while normalizing case. DOB is a validated YYYY-MM-DD date; creation is a server Timestamp and membership expiration retains Unix seconds for existing readers.
- Dev name/ID searches use normalized equality filters, always scoped by `access`. Other business searches retain legacy behavior. Results use 25-record cursor pages (26 fetched to detect the next page); no full collection download or growing prefix arrays. Search is exact, not fuzzy/substring. `searchEmail` and `productId` provide stable fields for future filters; those controls are not exposed yet.
- The deployed `members(access ASC, creation_time DESC)` index supports recent-member pagination. Read-only CLI inspection found no existing composite indexes in `cerms` on September 18, 2026. Equality-only filters use automatic indexes; production index readiness must be checked after deployment.
- Notes remain a bounded legacy array for reader compatibility. Future append-only notes/visits belong in independently paginated records rather than an ever-growing member document; this flow does not add editing or history writes.

## Atomic creation

One REST commit creates exactly three documents, each with `exists: false`: the member, `system/dev/memberIdentities/{sha256}`, and `system/dev/memberNumbers/{number}`. Reservations contain only `access: "dev"` and `memberId`. All three succeed or none do. Rules require reciprocal references to newly created records; claims cannot be updated/deleted or enumerated. Existing members cannot be overwritten. Random number collisions retry at most five times.

Identity is derived from business, selected issuing state/type, case-normalized government ID, and DOB. The fingerprint records the validated request contents. A retry with the same request UUID reads the previous result; changed request contents are rejected. A lost commit response triggers a read-back before reporting uncertainty. No raw barcode is saved or logged.

Duplicate prevention coordinates this writer. Rules do not recompute client SHA-256, so it is not protection against a malicious authorized owner deliberately supplying a different hash. Legacy records without claims are not imported into this Dev scope. Broad production rollout requires a reviewed identity policy, trusted shared allocation/claim logic, migration reconciliation, staff permissions, product configuration, and payment decisions. Hashes of identity data are not anonymization.

## Tera HW0008 scanner

The user's linked scanner is Tera HW0008. The [manufacturer](https://tera-digital.com/products/2d-barcode-scanner-hw0008) lists PDF417 driver's-license support, USB and 2.4 GHz wireless connections. Use its USB/receiver keyboard output with keyboard language matching the computer. Preserve barcode separators; do not configure it to strip or rearrange fields. On the Members page, Scan ID opens a read-only member lookup. Scan one card; lookup starts automatically after two seconds with no input. Every character resets the wait, including embedded line breaks. A four-second option accommodates slower output. There is no total scan-duration cutoff, so continuous slow typing is allowed. Manual Search members remains a fallback. Existing matches show name, DOB, state and a View member action. If no member matches, the owner in Dev System can explicitly choose Create membership with this ID; the scanned details are filled into the creation form for immediate review. A failed lookup never offers creation. Inside the creation form, automatic completion checks the current business for the ID; existing matches block saving and expose View member. With no match, fields fill automatically without an Apply/Continue step. Final member creation still requires an explicit save. Enter and Tab inside capture cannot submit membership creation. Escape clears capture. There is no global keyboard interception.

US AAMVA DL and ID text, ANSI headers, CR/LF/tab/record separators, DAC/DAD/DCS names, DCU or legacy DAE suffix, DBB DOB, DAQ ID and DAJ address state are supported. DBA expiration and truncation flags produce review warnings. DAJ is the address state, **not proof of issuing jurisdiction**; staff must confirm the issuing state on the physical card. The initial parser does not infer an issuer from IIN. Scanning does not authenticate a card or prove identity. Non-US, concatenated, repeated-field, invalid-date and oversized scans are rejected rather than guessed. No address, sex, height, eye color, document discriminator, or full raw scan is retained.

Field semantics were checked against [Virginia DMV's AAMVA calibration documentation](https://www.dmv.virginia.gov/sites/default/files/documents/VA-DMV-DL-ID-AAMVA.pdf). Tests use invented payloads. ## Scan lookup behavior

Lookups reuse the existing scoped, paginated government-ID reader with `dnaOnly: false`, so expired and do-not-admit members remain discoverable. They search by ID number without additionally filtering by DOB or address state, avoiding false negatives from changed or incorrect identity details. Dev uses the existing normalized ID key; other systems retain the existing exact legacy ID query. Multiple matches are shown for staff to disambiguate. Up to 25 are displayed, with a notice directing staff to the paginated ID search if there are more. Opening a match or a just-created member closes the creation dialog before opening member details. Dialogs do not stack. No new query shapes, backend rules, indexes, Auth accounts or write permissions were introduced for this UI change.

## Automatic scan completion

`IdScanInput` owns capture and its timer. It waits for an input-free interval (2 seconds by default, 4 seconds selectable), then requires successful decoding before invoking lookup once. It does not interpret Enter/Tab inside the payload as end-of-scan. Incomplete or unsupported payloads stay in capture for continuation or explicit clearing; they never auto-search. Raw input is cleared on successful decoding, explicit manual parse failure, cancellation, clear, and unmount. Closing capture cancels pending completion. No barcode text is logged or stored.

Idle completion is a keyboard-output heuristic, not a hardware completion signal. If a scanner pauses longer than the selected interval midway through an otherwise decodable payload, a premature lookup remains possible; use the longer delay for that device. Physical HW0008 timing still needs confirmation. Parser tests accept the standard DAJ address-state codes for all 50 states and DC, but do not certify every state's card/version. Older formats lacking DAC/DCS/DBB/DAQ, non-US formats, and stripped line separators remain unsupported.

Optional phone numbers are validated using libphonenumber-js full metadata (US default; international input requires + country code). Stored `phone` is E.164; blank input omits the field. Member details show formatted numbers. Extensions are not supported. Existing members need no backfill. The optional phone rule change is deployed with the nested reservation rules.
