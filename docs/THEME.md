# Account appearance preference

The workspace top-right moon/sun button switches light and dark mode. It is keyboard accessible, labels the next action and exposes the current dark state with `aria-pressed`. Existing profiles with no preference use light mode without a write. Sign-in and system switching load `users/{authenticated uid}.themePreference` from named `cerms`; the account preference follows the user across devices/businesses on subsequent sign-in. Signing out restores the light login screen without copying preferences to another account.

Only deliberate button activation calls `saveThemePreference`. The callable accepts exactly `{ theme: "light" | "dark" }`, derives the UID from verified authentication, requires an existing matching profile and updates only `themePreference`. It cannot provision profiles, set access/rank/permissions, change versions, mutate Auth or select another user. No timestamps or missing profile fields are invented. All staff may change their own appearance without sales/admin permission. No existing accounts are backfilled or modified during deployment/testing.

The UI updates immediately while the request saves, disables repeated toggles/system selection during saving, and restores the prior appearance with an error if saving is not confirmed. Request timeout is bounded; a response lost after a successful save can leave the profile updated, which will be read on next sign-in. There are no automatic retry or sign-in writes.

Shared CSS tokens support dark canvas/surfaces, inputs, dialogs, tables, navigation, catalog tiles and success/warning/error colors while retaining existing light colors. Product image content/category swatches keep their configured colors. The application theme does not change printer output or OS settings.

Desktop profile writes remain blocked except the existing UID-only access switch. Rules add optional enum validation to `validUser` so that switch still works with a saved preference; no client theme write permission is added. Exact release: `firebase/releases/theme-2026-11-13.rules`, tested byte-for-byte via `firebase/cerms.rules`. Existing business/record rules remain unchanged from the deployed checkout baseline. The current scoped configs reference this new release to preserve it on future deployments.

Deployment targets only `functions:cerms-staff:saveThemePreference` and the named `cerms` rules through `firebase.theme.json`. `scripts/theme-deployment.mjs before|after` checks the prior/exact resulting rules and verifies legacy/default/Storage rules, both databases' settings/indexes, both buckets and every existing function remain unchanged. Evidence: `docs/THEME-DEPLOYMENT.json` after verification. No Auth or Storage deployment occurs.

Validation: `npm run check` (174 client checks/build), `node --test functions/theme.test.mjs` (three synthetic server tests), `npm run test:rules` (315 isolated rules checks), and `node scripts/pos-smoke.mjs --theme` (all HTTPS intercepted). The desktop test covers a saved dark profile, both toggles, profile-only mutation, failed-save rollback, sign-out/in persistence without sign-in writes, POS and register dialogs. `npm run test:theme` bundles the focused build/server/desktop flow. No live profile writes or test accounts are used.
