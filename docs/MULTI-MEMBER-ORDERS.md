# Multiple memberships and rental recipients

The POS supports multiple pending new memberships and rental units in one order, including repeated purchases of the same product. **Order linked to** selects the purchaser/reference member independently of fulfillment recipients. It lists existing members chosen for the order and pending members represented by its membership items. **Find existing member** searches the current business by name, membership number or government ID, with paginated results. No existing member fields are edited by linking an order.

**Add membership**, or selecting a membership catalog product, opens the existing new-member form and appends its validated details to the current order. It does not replace the cart or save any member. Each unit requires its own pending member details. Removing a pending membership also removes its corresponding quantity; removing the linked pending member clears the order link. Removing a pending recipient clears explicit rental assignments to that recipient and requires a new assignment. The existing owner-only Dev System creation boundary remains; this does not enable existing-member renewals or wider member-creation permissions.

Repeated rental selection adds a distinct unit with a stable assignment ID, a required **Assigned Room/Number** and its own **Assigned to** selector. The default follows the order's currently linked member until explicitly overridden. Staff can assign a unit to a pending member or find another existing member without changing the order link. Explicit assignments survive changing the order link. Assignments remain free text; there is no room uniqueness or room inventory reservation feature. Existing active/DNA/expired/foreign-business recipient checks remain.

The cart groups units by product for consistent prices, taxes and inventory accounting. Membership/rental quantities are derived from pending member details and unit assignments, rather than a manually editable quantity. Retail quantities remain editable. Pending memberships, known existing members, per-unit rental assignments, the primary order link and stable IDs persist in the staff/business-scoped local draft. An uncertain checkout locks all order changes for the identical-request retry, including every recipient. Recovery preserves a valid pending checkout request even if other local draft data cannot be decoded.

The callable accepts optional `pendingMembers` alongside a primary `member` reference, plus rentals containing `id`, `productId`, `memberId` and `assignedRoom`. Older single-member requests (including old pending retries with `member.draft`) remain supported without rewriting their fingerprint. New requests are limited to 20 pending memberships, 100 rental units, 50 involved members and 100 unique product lines. The desktop callable request guard remains restricted to the same exact endpoint and permits bounded group requests up to 500,000 characters.

`completeSale` revalidates each member against the named `cerms` database. Membership quantities must exactly match pending member details for the product; rental quantities must exactly match assignments. Duplicate pending IDs/identities, missing quantities, duplicate rental IDs, unavailable products, invalid recipients and insufficient payment/stock reject the entire transaction. The server reads all participant documents, identity/number reservations and admission claims before staging any writes.

One transaction creates every pending member and its reservations, one active activity record per rental unit, one admission claim per recipient, existing-recipient `checkedIn` updates, the receipt, inventory changes and register totals. Several rentals for the same member share one claim with multiple visit IDs. New activity IDs are `{saleId}_{rentalAssignmentId}`; legacy single-product assignment IDs continue to be supported. The purchaser is not checked in unless they receive a rental. No client-side fulfillment writes are added.

Receipts retain the primary member, server-derived involved-member snapshots and explicit membership/rental recipient IDs. They never store member drafts, government IDs, birth dates or notes. Printed receipts show membership recipients, rental recipients and room/number assignments. Sales search includes all involved member names, IDs and numbers. Existing live admissions subscriptions decode the individual activity records without query or rules changes.

Verification: twelve synthetic server checkout tests, client request/receipt tests, and the fully intercepted Electron `node scripts/pos-smoke.mjs --group` flow cover multi-member atomicity, repeated product units, independent recipients, default/override behavior, draft restoration and lost-response retries. Existing single-member and retail POS flows remain compatible. `npm run test:checkout` runs both member flows. No production members, rentals, orders, accounts, emails or print jobs are used for testing.

Deployment changes only `functions:cerms-staff:completeSale` through `firebase.checkout.json` under the standing compatibility authorization. Rules remain exactly `firebase/releases/checkout-2026-10-11.rules`; no indexes, Auth, Storage or other functions are changed. `scripts/checkout-deployment.mjs before|after --group` compares the current live baseline and all legacy/shared metadata. Evidence is recorded in `docs/MULTI-MEMBER-ORDERS-DEPLOYMENT.json` after verification.
