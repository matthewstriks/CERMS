# Linked membership and rental checkout

New membership forms now continue to Point of sale with the selected catalog membership and a pending member linked. Nothing is written when the form is submitted, the cart is canceled, or payment is abandoned. The existing owner-only Dev creation boundary remains. An open personal register and POS permission are required to complete any order. CERMS records externally received payments; it does not process cards.

Multiple-membership and rental-recipient orders now extend this flow; see [Multiple memberships and rental recipients](MULTI-MEMBER-ORDERS.md) for the current quantity and assignment model. The original single-member flow described below remains supported for old requests.

The member table offers **Create order** and **Check in** to staff with `processSales`. Create order starts a member-linked cart; Check in first shows active, permitted rental products, then continues to the complete order where other items can be added. Each rental type is one unit for the linked member and requires a nonblank **Assigned Room/Number** (maximum 120 characters). Membership renewals are outside this flow; membership products enter checkout through the new-member form.

`completeSale` revalidates saved staff/business access, personal register ownership, catalog versions/prices/availability, taxes and payments. In a single named-`cerms` transaction it creates the sale and register totals, adjusts inventory, and fulfills the linked member/rentals. New member documents retain the established schema, normalized search fields, minimal contact fields and atomic identity/number reservations beneath `system/dev`. Membership expiration starts at successful checkout. The member stores `orderId`; receipts store a server-derived member ID/name/number snapshot without the draft's identity, birth date or notes.

Rental fulfillment requires an active, non-DNA member in the same business. It creates one `activity/{saleId}_{productId}` record per rental with `access`, `memberID`, `active: true`, `currIn: true`, `timeIn`, `orderId` and the existing `lockerRoomStatus` representation. Slot 1 contains the assigned room/number; slots 4/5 contain server-derived rental start/expiration seconds. This preserves the existing `active == true` / `access == current business` subscription and `goingInactive` filtering in Overview and Admissions & rentals. Existing member updates here change only `checkedIn` to true.

A server-only `system/{business}/memberVisits/{memberId}` claim serializes competing checkouts for that member; existing `checkedIn` state is also checked. Duplicate admission is rejected. Checkout/out, rental extensions, waitlist changes, room availability/uniqueness management and removal of visit claims are outside this request. Assigned rooms/numbers are free text, not room inventory reservations.

The complete request is persisted in the existing staff/business-scoped local POS draft before submission. An uncertain save locks the order for an identical retry, including member ID and rental assignments. A prior committed sale returns its receipt even if catalog/register state subsequently changes. There are no separate post-sale client fulfillment writes. A confirmed rejected request can return to the cart; an unknown outcome must be resolved before another order starts. New-member form details remain only in the local draft until successful checkout or clearing that draft. They are never copied onto a receipt.

Direct desktop member-creation commits are now blocked by both the request guard and the named `cerms` rules. Server fulfillment uses the existing callable/Admin SDK restricted to named `cerms`; no desktop Admin credentials or new client write exception is added. Existing member management permissions and the read-only admissions subscription remain in place.

Shared member validation and encoding are bundled into `functions/checkout-domain.mjs` by `npm run build:checkout-domain` from `scripts/checkout-domain.ts`; edit the shared TypeScript sources and regenerate before deployment. `npm run test:checkout` builds and runs server tests plus an Electron flow with all HTTPS intercepted. `npm run test:rules` runs the exact rules in isolated `demo-cerms-rules`. No live sales, members, rentals, emails, Auth changes or print jobs are used for tests.

Deployment uses `firebase.checkout.json`, targeting only `functions:cerms-staff:completeSale,firestore:rules` for project `cerms-7af24`. The config contains only the named `cerms` rules target, archived at `firebase/releases/checkout-2026-10-11.rules`. Read-only before/after checks in `scripts/checkout-deployment.mjs` compare default rules, shared Storage rules/bucket, both database configurations/indexes and every other function. See `docs/MEMBER-CHECKOUT-DEPLOYMENT.json` for published evidence when verification completes.
