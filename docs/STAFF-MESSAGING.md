# Staff messaging

Messages now supports private direct and group conversations between staff in the signed-in staff member's saved business. **New conversation** searches the complete paginated directory by staff name or ID; selecting several people starts a group of up to ten participants. Selecting the same participant set resumes its existing conversation. Directory responses contain only verified staff names and UIDs, never emails, ranks, permissions or other profile fields. No general staff-profile read access is added.

Conversation lists and messages update through read-only Firestore subscriptions. The sidebar shows message previews, times, unread indicators, an Unread filter, name/preview search and older-conversation pagination. Each conversation has chronological messages with verified sender names and local display of server timestamps, older-message pagination, multiline text entry, per-conversation in-memory drafts, and message-text search. **Search older history** scans further pages until the full history is searched; no indexed full-text search or silent truncation is claimed. Messages and participant sets are immutable.

Read receipts use a per-participant sequence watermark. The desktop acknowledges the latest rendered message only while that conversation has fresh server data, the window is focused and visible, the user is at the bottom, and history search is closed. Hidden windows, background conversations and older-history browsing do not mark new messages read. The server derives the sequence from a stored message and only advances the authenticated caller's marker, with their verified name and a server timestamp. Outgoing messages show Sent or Read, and group receipts identify which staff have read them. Expanded receipts show the participant's **last read** time; it is not presented as the original first-view time of each older message. Sending alone does not mark other messages read.

A lost send response preserves the original request ID and text for **Retry same message**. The server atomically stores one immutable message and advances the chat sequence and last-message metadata, making repeated requests harmless. An in-memory outbox survives reopening the Messages route during the same session and clears when the signed-in identity changes or signs out. Drafts and message history are not written to localStorage or disk caches by this feature. Message delivery is confirmed only by the saved server record; no device-delivery claims or external emails/push notifications are generated.

## Storage and authorization

The authenticated `staffMessaging` callable runs only against named `cerms` and supports bounded `directory`, `start`, `send`, `read` and `search` actions. It checks the caller's existing saved profile and business on every request. Conversation creation and new sends revalidate every recipient's current business. If a participant moves away, remaining participants retain their history, but new delivery requires a conversation with current staff. Nonparticipants, including the fixed owner, have no messaging-content override.

New paths are `system/{business}/staffChats/{chatId}` and `system/{business}/staffChats/{chatId}/messages/{requestId}`. Conversation IDs are a hash of the sorted participant UIDs within that business; message IDs are stable request UUIDs. Message text is limited to 10,000 characters. Sender names/UIDs, timestamps, sequence numbers and receipt identities are server-derived. Direct desktop writes to chat/message documents remain denied by both rules and the network guard. Legacy root `chats`/`messages` collections are neither read nor migrated.

The new composite index is COLLECTION scope on `staffChats`: `participantUids ARRAY_CONTAINS`, `updatedAt DESCENDING`. The two existing `cerms` indexes remain unchanged. Private read rules require current saved-business access and membership in the conversation; history and conversation queries are limited to 50 records. Staff directory queries and history-search scans are server-only. Existing admissions and messaging share one in-memory full SDK client, fixed to `cerms`; the existing Lite client and blocked Firestore Write stream are preserved.

No staff Auth accounts, access profiles, employee permissions, memberships, rentals, sales, registers, Storage objects or legacy records are modified by messaging. No message editing/deletion, participant reassignment, legacy history copying or cross-business messaging is enabled.

## Verification and deployment

- `npm run check` covers the desktop build, client access boundary, read-state presentation and uncertain-send retries.
- `node --test functions/staff-messaging.test.mjs` covers directory pagination/privacy, deterministic groups, authenticated sender/time, duplicate-safe sends, monotonic per-staff receipts, nonparticipant/owner exclusion, access changes and paginated history search.
- `npm run test:rules` uses the isolated `demo-cerms-rules` emulator for participant/privacy/write-denial checks. It also exercises real Admin SDK transactions with concurrent sends/read receipts and real history/search queries, without production credentials or data.
- `npm run test:admissions` checks the existing live reader against its isolated demo emulator.
- `node scripts/messaging-smoke.mjs` intercepts all HTTPS and exercises the complete Electron flow, including search beyond the first directory page, groups, history, retries, hidden-window receipt protection and unread navigation. `npm run test:messaging` runs the focused build/server/UI workflow.

Standing Firebase authorization applies to only the new `staffMessaging` function, named-cerms messaging read rules and the new index. Deployment configuration: `firebase.messaging.json`; exact rules archive: `firebase/releases/messaging-2026-11-15.rules`. `scripts/messaging-deployment.mjs before|after` compares database settings, legacy/Storage rules and indexes, both existing buckets, existing cerms indexes and every other function. Completion requires the new function ACTIVE and new index READY. Evidence: `docs/MESSAGING-DEPLOYMENT.json` after verification. No live test messages, read receipts, account changes or other production test writes are permitted.
