# Account settings

Settings → Account settings is available to every signed-in staff member for their own account. No staff-administration permission is required. The owner remains identified by the fixed UID, never the editable email.

- **Display name:** updates only the existing named-cerms profile’s `displayName`, with an exact version precondition. The workspace reloads its profile after saving. Shared Auth display names and legacy profile documents stay unchanged.
- **Email:** requires the current password and sends Firebase’s verify-before-update email. The existing login email remains active until the new address is verified. The interface states that credential changes also affect legacy CERMS because Auth is shared. No direct/unverified email-update endpoint is allowed.
- **Verification:** sends a Firebase verification email to the current login email on demand. Refresh verification reloads the current user, obtains a fresh token, and deliberately syncs a verified login email to only their existing cerms profile’s `email`. Settings loading and login never sync/write profile fields automatically. Firebase may expire an existing session after an email change; sign in using the verified new email and refresh verification to complete profile sync.
- **Password:** requires the current password, a new 12–128 character password and matching confirmation. Reauthentication occurs before the password update. Password fields clear after operations; passwords are never sent to the CERMS callable, stored in Firestore or logged.

The new `accountSettings` callable uses the existing named-cerms support identity, reads/writes only `users/{authenticated uid}`, rejects target UIDs/extra fields, preserves access/rank/version/preferences and unrelated fields, refuses missing profiles and rejects stale profile updates. Email sync derives only from signed Firebase email/email_verified token claims; the desktop forces a token refresh first. The service has no Firebase Auth mutation dependency and grants no admin account-editing rights.

The renderer guard permits only tightly shaped password updates and verification/verify-before-change email requests in addition to existing sign-in/reset operations. Account deletion, sign-up, arbitrary Auth profile updates, direct login-email changes and direct Firestore profile writes remain blocked. No custom redirect/continue URL is accepted; Firebase’s hosted action handler processes verification links.

Deployment scope is only `functions:cerms-staff:accountSettings` via `firebase.account-settings.json`. No Auth provider/template configuration, rules, indexes, Storage, legacy profile documents or existing functions are changed. Deployed November 17, 2026 and verified ACTIVE; evidence is recorded in [ACCOUNT-SETTINGS-DEPLOYMENT.json](ACCOUNT-SETTINGS-DEPLOYMENT.json). All existing functions, rules/indexes, both databases’ settings, bucket/IAM/secret policies and schedules were verified unchanged. The existing staff admin edit/removal boundary is unchanged: admins still cannot change other people’s shared login credentials.

Focused verification uses two synthetic server checks, two client/guard checks and an isolated Electron flow for name save, verification mail, wrong-password denial, email confirmation/sync and password confirmation/update. Every network effect is intercepted, including Auth, token refresh and email sends. Typecheck and a desktop build support the flow; builds were repeated only for fixes uncovered in that flow (the resend timer and main-process password-request body forwarding). No real emails, account mutations, production test writes or release packaging. Real inbox delivery is not tested.
